An OEE dashboard built around the decisions a shift supervisor makes. Follow production losses from plant to line to machine, with consistent KPI definitions and a traceable data model.

Business problem

Output was tracked on paper shift reports and copied into separate spreadsheets. Each line calculated “efficiency” differently, downtime reasons were free text, and the daily meeting spent its time arguing about the numbers instead of acting on them.

Goal: one trusted source for OEE and its losses, with definitions everyone agrees on. A supervisor should be able to answer three questions in under a minute: Are we on target? Where are we losing time? Which machine or shift needs attention today?

Data model

A star schema rather than one flat sheet. Production and downtime have different grains: one row per machine-shift, and one row per stop. They live in separate fact tables, and the shared date, shift and machine dimensions filter both at once.

The two fact tables are never joined directly. A slicer on line, machine or shift filters both through the dimensions, so downtime always ties back to the same production rows.

KPI definitions & DAX

KPIDefinition
Planned production timeShift length minus scheduled breaks: 450 min per machine-shift
AvailabilityRun time ÷ planned production time. Changeovers count as a loss, because they are a target for SMED.
Performance(Total count × ideal cycle time) ÷ run time. Captures minor stops and slow cycles.
QualityGood count ÷ total count. Rework counts as not good.
OEEAvailability × Performance × Quality. Target 75%.
First-pass yieldGood first time ÷ total. Equal to the OEE quality factor here, because each cell is one operation.
Scrap rateScrap count ÷ total count
Target attainmentGood count ÷ planned good count (75% of ideal output)
 
// Core measures (full file: analysis/oee_measures.dax)
Ideal Run Time (min) =
SUMX ( fact_production,
    fact_production[total_count] * RELATED ( dim_machine[ideal_cycle_s] ) / 60 )

Availability = DIVIDE ( [Run Time (min)], [Planned Time (min)] )
Performance  = DIVIDE ( [Ideal Run Time (min)], [Run Time (min)] )
Quality      = DIVIDE ( [Good Count], [Total Count] )
OEE          = [Availability] * [Performance] * [Quality]

Downtime Share =
DIVIDE ( [Downtime (min)],
    CALCULATE ( [Downtime (min)], REMOVEFILTERS ( fact_downtime[reason] ) ) )

OEE is calculated from summed times and counts, never by averaging machine OEE percentages. An average of ratios would give a low-volume machine the same weight as a high-volume one.

Decisions it supports

1
Run a SMED project on Line 1 changeoversChangeover is 54% of all downtime. Line 1 made 616 changeovers averaging 45 minutes; Line 2 averages 29. Separating internal from external work and pre-staging molds and materials is the first step.
2
Put M5’s mold on preventive maintenanceM5 lost 4,969 minutes to mold and tool repair, 43% of the plant total and about four times any other machine. It also has the highest scrap rate (2.3%). Both point at the same tool.
3
Close Shift C’s performance gap, and log whyShift C loses on performance (84.1% vs about 89%) and scrap (2.3% vs 1.5%), not just on stops. Minor stops are not reason-coded today, so the first action is to log them, then compare start-up and staffing practices with Shift A.

Deliberately not concluded: that Line 2 needs no attention. It beats target overall, but M5 is pulling it down.

Estimated impact

If Line 1 changeovers matched Line 2’s 29-minute average, the line would recover about 9,700 minutes over the 13 weeks. That is +3.1 points of availability, lifting Line 1 OEE from 74.2% to about 76.8% and putting it above target, with performance and quality held constant.

This is an estimate from the model, not a measured result. Before claiming savings, a SMED pilot on one machine would be measured with this same dashboard.

Keeping the numbers trustworthy

  • Validation on every load: good + scrap + rework must equal total, downtime can never exceed planned time, and every stop needs a reason code from a fixed list. The build script asserts the first two.
  • One definition, two implementations: OEE by machine is also written in SQL, and the build fails unless SQL and the model agree for all six machines.
  • Ownership and cadence: refreshed daily before the tier-1 meeting. Each line lead owns their reason codes, and KPI definitions change only through the CI lead.
  • Review loop: each week, the top downtime reason becomes an action item with an owner and a due date, tracked on the next week’s Pareto.
